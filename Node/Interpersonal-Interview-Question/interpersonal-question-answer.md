### 9. How do you handle criticism?

Answer:
I try to separate the criticism from my ego.
For example, if a senior developer tells me that my implementation is unnecessarily complicated, my first reaction shouldn't be to defend my code. I would ask why they consider it complicated and what alternative they would suggest.
If their reasoning makes sense, I’ll change my approach. Even if I disagree initially, I would rather understand their perspective first.
As a fresher, I see code review as one of the fastest ways to improve.

### 10. How do you handle feedback on your code?

Answer:
I actually consider code review an important part of learning.
If someone points out an issue in my code, I don't only want to fix that particular line. I try to understand the principle behind the feedback so I don't repeat the same mistake elsewhere.
For example, if I'm told that my API error handling isn't consistent, I would look at the overall error-handling strategy instead of just changing one endpoint.

Teamwork & Collaboration

### 11. Do you prefer working alone or in a team?

Answer:
I’m comfortable with both, but I understand that professional software development is usually a team activity.
I can work independently when I’m given a clear task, but I also like discussing architecture, implementation decisions, and problems with other developers.
I think the important thing isn't whether I prefer working alone or with a team. It's knowing when independent work is appropriate and when collaboration will produce a better result.

### 12. What would you do if you disagreed with a senior developer?

Answer:
First, I would try to understand their reasoning instead of immediately defending my own approach.
If I still believe my approach has an advantage, I would explain my reasoning with technical evidence—for example, performance, maintainability, simplicity, or security.
But once the team makes a decision, I would support that decision unless there is a serious technical or security concern that needs to be escalated.

### 13. What if your teammate makes a mistake?

Answer:
I would first understand whether the mistake is something I can help fix directly.
If it affects the project, I wouldn't focus on blaming the person. I would focus on solving the problem and preventing it from happening again.
For example, if a teammate introduces a bug, I might help reproduce it, explain what I found, and suggest adding validation or a test if appropriate.
I believe a good team should solve problems together rather than create a blame culture.

### 14. What if a teammate isn't contributing?

Answer:
I wouldn't immediately assume they're being irresponsible. First, I would try to understand whether they're blocked or unclear about their task.
I might ask something like, “Are you blocked on anything? I was working on this part and maybe I can help.”
If the problem continues and starts affecting the project deadline, I would communicate the situation to the appropriate team lead with facts rather than personal accusations.

### 15. How would you explain a technical concept to a non-technical person?

Answer:
I would avoid technical terminology unless it is necessary.
For example, instead of explaining an API using HTTP methods and status codes, I might say that an API is like a communication layer between two parts of a system: one side asks for something, and the other side processes the request and sends back the result.
My goal would be to make the concept understandable, not to demonstrate how much technical vocabulary I know.

### 16. How do you communicate when you're stuck?

Answer:
I first investigate the problem myself. I check the error, reproduce it, read the relevant documentation, and try a few reasonable approaches.
If I'm still blocked, I don't just say, “It's not working.”
I would explain:

- What I'm trying to achieve
- What I expected
- What actually happened
- What I've already tried
- Where I think the problem might be
  That makes it much easier for another developer to help me.

Pressure & Problem Solving

### 17. How do you handle pressure?

Answer:
I handle pressure by breaking the problem into smaller tasks rather than trying to solve everything at once.
For example, if I had a deadline for an API project, I would separate the work into authentication, database models, core APIs, validation, testing, and documentation.
Then I would prioritize the functionality that is essential for the deadline.
Pressure becomes much easier to manage when the work is visible and prioritized.

### 18. What would you do if you had a deadline tomorrow and your feature wasn't complete?

Answer:
First, I would determine exactly what remains and separate the essential functionality from the nice-to-have functionality.
Then I would communicate the situation early rather than waiting until the deadline.
If necessary, I would prioritize a stable, smaller version of the feature over an incomplete complicated version.
I would also make sure the team knows the remaining risks and what could realistically be delivered by the deadline.

### 19. What if you receive three urgent tasks at the same time?

Answer:
I would not simply start working on whichever task appeared first.
I would clarify the priority based on business impact, dependency, deadline, and severity.
For example, a production bug affecting users would normally take priority over a minor UI improvement.
If the priorities aren't clear, I would ask my team lead rather than making an assumption that could waste time.

### 20. How do you deal with failure?

Answer:
I try to treat failure as information.
During project development, I've had implementations that didn't work as expected. Instead of simply replacing them, I try to understand why they failed.
For example, if an approach causes unexpected API behavior, I want to know whether the problem was in the design, implementation, assumptions, or testing.
That mindset helps me avoid repeating the same mistake.

Learning & Growth

### 21. How do you learn a new technology?

Answer:
I usually start with the official documentation and basic concepts instead of immediately jumping into a large tutorial.
Then I build something small with it. After understanding the fundamentals, I use it in a larger project.
For example, when learning backend technologies, I don't want to memorize commands. I want to understand what problem the technology solves, how it works, and where it should or shouldn't be used.

### 22. What do you do when you don't know the answer to a technical question?

Answer:
I would be honest and say that I don't know rather than trying to guess.
But I would also explain how I would find the answer.
For example, I might say, “I haven't worked with that specific feature yet, but I would first check the official documentation, understand the underlying concept, and then create a small example to verify my understanding.”
I think being honest about what I don't know is better than giving a confident but incorrect answer.

### 23. How do you keep yourself updated?

Answer:
I primarily follow official documentation and release notes for technologies I'm actively using.
I also learn through practical projects. If a technology introduces a new feature that solves a problem I'm currently facing, I try to understand it through a small experiment.
I don't try to learn every new technology just because it's trending. I prefer building strong fundamentals and then learning tools that are relevant to my work.

Behavioral / Situational Questions

### 26. Tell me about a time you solved a problem independently.

Answer:
While working on my projects, I encountered several backend issues where an API worked locally but behaved differently after deployment.
Instead of immediately changing random parts of the code, I started checking the production logs, environment variables, database connection, and runtime configuration separately.
This taught me to debug systematically instead of relying on trial and error.
That approach has become one of the habits I want to carry into professional development.

### 27. Tell me about a mistake you made in a project.

Answer:
One mistake I made early in development was focusing too much on implementing features before thinking deeply about the overall structure.
As the project grew, some changes became harder because different parts were too tightly connected.
I learned that spending some time designing the database relationships, API structure, and responsibilities of different modules early can save significant time later.

### 28. Tell me about a time you had to learn something quickly.

Answer:
When working on backend projects, I sometimes encountered technologies or concepts that weren't part of my earlier coursework.
Instead of trying to learn everything at once, I identified exactly what the project required, learned that specific concept, and implemented a small working example first.
Once I understood the fundamentals, I integrated it into the actual project.
That experience taught me that learning quickly doesn't mean skipping fundamentals; it means focusing on the fundamentals that are immediately relevant.

### 29. What would you do if you realized your code was wrong after submitting it?

Answer:
I would communicate it as soon as I discovered it.
I wouldn't try to hide the mistake just because the code had already been submitted.
I would explain what went wrong, assess the impact, propose a fix, and if appropriate add a test or validation to prevent the same issue from happening again.
I believe transparency is especially important in software development because small hidden mistakes can become larger production problems.

### 30. What would you do if your manager gave you unclear requirements?

Answer:
I would first try to identify exactly what is unclear instead of asking a very general question like “What should I do?”
Then I would ask specific questions about expected behavior, edge cases, priority, and acceptance criteria.
If possible, I would also summarize my understanding back to the manager, such as: “My understanding is that the feature should behave like this—is that correct?”
That reduces misunderstandings before development starts.

### 31. What would you do if you found a security vulnerability in your team's code?

Answer:
I would treat it seriously and report it through the appropriate internal process.
I wouldn't publicly discuss or exploit the vulnerability.
I would first understand the issue well enough to explain its impact, then inform the responsible senior developer or security team and help implement a proper fix.
Afterward, I would also consider whether tests, validation, or development practices could prevent similar issues.

### 32. What if you strongly believe your technical approach is better?

Answer:
I would present my reasoning rather than simply saying my approach is better.
For example, I might compare the two approaches based on complexity, maintainability, performance, security, and future changes.
If the team chooses the other approach after discussion, I would respect the decision unless there is a serious technical risk.
Software engineering is a team activity, so being technically correct isn't the only consideration.
